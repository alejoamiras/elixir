Blueprint · deep · yacana-surfaces · approved 2026-09-05

Rename to Yacana and build the miner, the stats and the landing on one site

Five stacked pull requests. First the project changes its name everywhere, including inside the circuit, and gets a fresh testnet deployment. Then a shared design system, the new miner (passkeys, a key vault, private or public withdrawals, the power slider, every win and failure state), a stats page that reads the chain straight from your browser, the landing page with a real proof you can run, and the machinery that puts all three on yacana.network, built and previewed by Cloudflare from the repo.

Why the heaviest planning tier

Five of the six risk dimensions are high: novelty (passkeys and a key vault are new to this codebase), blast radius (every surface plus the contracts' name), irreversibility (a new deployment; a passkey is bound forever to the hostname it was created on), external coupling (Cloudflare, the Aztec node, browser passkey platforms) and security sensitivity (keys, money). So: three independent plans (this session, codex, a second Claude), a consolidation with a decision ledger, a contradiction check by both reviewers, a double audit, and a final fresh-eyes codex pass. The final pass returned conditional approve; its four conditions (safer previews, gap-free recovery, a tighter vault record, type-checking every gate) are applied in the plan. Recon used 2 agents; code-review is off, the codex fix loop is the review.

What was decided along the way

questionanswerwhy
Where does the secret live?Not on disk, by default. A passkey key is re-derived from the passkey every time you open the miner (one touch). Twelve-word keys are sealed with a device key, with the limit stated honestly.The audit found the embedded wallet's own database writes the secret key in cleartext. So the wallet now runs in memory and the vault owns the secret.
How do the stats read the chain without a server?The browser reads public storage directly: the open epoch, the last 48 epochs, the total supply. A small build-time table replaces a 3 MB hashing library.You said no indexer. The one thing lost is the exact "last claim N minutes ago"; it becomes "open epoch: 2 claims, opened 3 min ago".
What if a claim loses a race?The miner re-syncs that key's local view of the chain and carries on; nothing is lost. If that ever fails to unblock, it pauses and says when it can claim again.Aztec's local client refuses to forget a lost send until L1 has finalized it (tens of minutes). You dropped the "second account" workaround; the re-sync is simpler and the plan verifies it end to end.
How does the landing prove for real?It borrows the miner's proving Worker, loaded only when you click "Prove one now". Desktop only.Two of three planners preferred this over an iframe; it keeps one headers policy for the whole site.
Who deploys?Cloudflare itself: the repo is connected to the Pages project, main builds production, every other branch gets a preview link on its PR. No Cloudflare token exists in GitHub.Your call. It also removes the token-handling problems two codex rounds found. The price: the compiled contract artifacts are committed so Cloudflare's builder needs only Bun, and CI checks they stay fresh.
Can a link trick the miner?No longer: production builds ignore ?miner=&token= in the address bar; only local test builds honour them.Today any link can point the page at a fake deployment on the allowed node.

Arc 2 · the miner (one PR, five phases)

The M1 cockpit, passkeys first with the twelve words behind a small link, the key vault, wallet and withdraw, and every state the binder drew.

P2.1 Site tooling and the shell

One configuration source for all three sites with yacana.network as the passkey hostname, one headers policy rendered per environment, the miner under /mine, the phone stop-screen, the host rules (the pages.dev alias redirects, previews show a banner and never create keys), the link-override guard.

P2.2 Cockpit, power, settings

Proves itself by: reducer and metric unit tests; an end-to-end run that changes the power three times while mining continues and memory does not grow.

P2.3 Passkeys and the vault

The riskiest phase: the passkey ceremony, the key derivation with pinned vectors, the in-memory wallet, the vault, the "ask every open" default.

Proves itself by: derivation vectors, vault tamper tests, and an end-to-end run with a virtual passkey that creates a key, mines, claims, reloads and comes back with one touch, with no secret found on disk.

P2.4 Twelve words, wallet, withdraw

Proves itself by: the write-down quiz and phrase validation tests; end-to-end: create with words, forget, restore to the same address; withdraw privately to a second key and publicly to an address.

P2.5 The win beats and every failure

The stepper with the real expiry countdown, the marks at the mint, the lost-race re-sync, expired claims, node unreachable, prover dead, notifications, the mini window; an upstream issue filed for the client behaviour.

Proves itself by: unit tests for every transition; end-to-end: the node drops and mining pauses then resumes; a real lost race is forced on the isolated network, the key re-syncs, the next claim mints and the balance survives.

Human context

Three things the reviewers pushed on hardest. Passkeys have no backup by design: you chose one method per key and no 24-word export, so if a passkey is lost or its provider does not sync the secret, the balance is stranded; accepted for testnet, the page says so and nudges people to move funds, and it is revisited before mainnet. One origin means one policy: the landing, the miner and the stats share headers, so a mistake in one bundle reaches all three; the headers are generated and pinned by a test. Nothing deploys to the new domain until arc 4: that removes every "migrate old data" problem, because the new site starts empty.

Decisions you made at approval

  1. Passkey backup: none. Risk accepted for testnet with a warning and a move-funds nudge; revisit before mainnet.
  2. Rotation: dropped. One account per key; a lost race is recovered by re-syncing the key from the chain.
  3. No interim deploy: the first deploy is arc 4.
  4. Hostname: yacana.network, bought, zone on Cloudflare. Source: github.com/alejoamiras/elixir, to be renamed alejoamiras/yacana (no org; GitHub redirects the old name). X handle: placeholder until you give it.
  5. Public node load: accepted for testnet.
  6. The old Elixir site: retired once the new domain is live.
  7. Previews: yes, on every PR, built by Cloudflare's Git integration. No token in GitHub.
  8. The old deployment record moves to a dated filename.
  9. Cloudflare: you connect the repo to the Pages project; no token needed. The testnet deploy in arc 0 runs with your secret supplied through the environment.
