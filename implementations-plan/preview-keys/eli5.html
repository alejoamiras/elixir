Preview Keys

Let a reviewer actually use the miner on a branch's Cloudflare preview: sign up, mine, claim, withdraw on the testnet. Today every preview shows a banner and greys out sign-up, so a PR that touches the miner can only be reviewed from a local checkout.

What changes, in one breath

The page already asks "where am I being served from?" before it lets anyone make a key. Right now the only answer that unlocks keys is yacana.network. After this change, this project's own preview addresses unlock keys too, and a passkey made on a preview is tied by the browser to that exact preview address. Everything else stays locked.

The preview address pattern lives next to the production domain in the site's one public config file. Test builds leave it empty, so nothing is a preview there.

What you get as a reviewer

  • Open the branch's preview link from the Cloudflare check, go to /mine/, sign up with a passkey or twelve words, mine, claim, send. Same bundle, same testnet, same node rules as production.
  • Use the branch address (the one with the branch name in it), not the per-push one: each address is its own browser origin with its own vault and its own passkeys.
  • Treat preview accounts as disposable. The banner says so.
The one thing to remember: twelve words are the same account everywhere. Never type your yacana.network words into a preview, and never carry preview words to yacana.network. A branch is code you have not reviewed yet; the page cannot stop it from reading what you type. Passkeys do not have this problem: a production passkey simply cannot be used from a preview, and vice versa.

Why light, and what codex said

Rubric: no novelty (the host rule and passkey plumbing exist), small blast radius (one function, one getter, copy), reversible, no migration, no new external coupling. Security sensitivity is the one dimension that is real, and it is why the plan went through a codex round that changed it: the first draft would have unlocked keys on any workers.dev address, including a stranger's copy of the site. The final rule names this project's addresses only.

Settled between me and codex (not sent back to you)

  • Passkeys on previews, tied to the exact preview address. Words-only would have left the default sign-up path untested.
  • Words stay portable. Making preview words derive a different account would not stop a bad branch from reading the phrase, which is the real risk; it would only add a second key scheme. The banner warns in both directions instead.
  • No new build mode. A preview is the production bundle; the address decides at runtime.
  • No fake-domain browser test. A real preview domain needs real TLS to test passkeys; instead the rule gets a full table of addresses in unit tests, the miner session gets a test proving which address reaches the passkey call, and the existing local browser suite stays as the net. The first live sign-up on this branch's own preview is recorded in the PR.

The one phase

P1 — the named preview address, the passkey domain, the copy, the tests, the docs

Proves itself by: lint clean, the miner's component tests (the address table) green, the unit tests for site config and the miner session green, and the miner's cockpit browser shard still green on localhost.

Then the codex fix loop on the diff until a round finds nothing material, then one PR. Merging stays your call.
