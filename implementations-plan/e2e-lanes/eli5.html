Faster miner tests

The miner's browser suite is nineteen tests. It takes about sixteen minutes here and forty in CI, on one machine, and it only runs when someone asks for it by hand — so nothing about the Mine page is checked when you push. This plan makes it faster and gives it a small lane quick enough to run on every push. It also does something less comfortable: it says plainly which of the speed-ups cost you test coverage, and puts that decision in front of you with a number attached instead of burying it.

The short version of what happened

I wrote a plan. Two reviewers read it and both rejected it, for reasons that turned out to be right when I checked them against the code. I rewrote it. A third reader called the rewrite sound in shape but too vague in its promises, and I tightened it. The plan below is the third version, and most of what makes it good came from being wrong twice.

I planned toInstead
Build a lane that skips the chain entirely, for the tests that never touch itImpossible. The page refuses to show its sign-in screen until it has checked a real node and a real deployment. Those tests need a chain even though they never use one.
Invent a way to run the app with no node behind itYou already have one. The stats screenshot gate records every answer the page needs once, then replays them with no node at all — and it runs on every pull request today. The miner's fast lane copies it.
Sort every test into categories and build a machine to serve each categoryDropped. Both reviewers worked out that the machinery could only ever skip one deployment, two proxies and one helper process. Two switches do that. The categories bought nothing.
Turn off the slow proof in most tests, early, as the third of four stepsMoved to last, made optional, and might never happen. Nobody has measured whether that proof is actually where the time goes.
Claim four safety barriers keep that switch out of the real siteThere is one. Two of the four share a single condition, one of them is unreachable code that can never fire, and the test whose name says it covers them does not.

Two things worth knowing regardless of this plan

A single misspelling would open the front door. The site decides whether it is a production build by reading one environment variable and trusting it without checking. Any value other than the exact word production — a typo, a stray capital — re-enables every test-only override and loosens the security policy the real site ships with. That is a three-line fix, and this plan now does it first, on its own, whether or not the rest is ever built.

Your test network has never checked a proof. The local chain the tests run against is configured to accept fake proofs, and it installs a verifier that answers "valid" to everything. So the value of the slow real proving in your tests was never that the network checked the work — it is that the claim's own circuit has to hold together mathematically, which is what catches a bad mining proof. That makes the case for keeping some real proving stronger and more specific than I first wrote, and it means the honest test for it is not "a claim worked" but "a deliberately broken proof was refused".

Why this tier

Scored against the six risks: nothing novel, small blast radius, nothing irreversible, no migration, no outside dependency — and one genuinely high one, which is that this plan touches the switch that turns proving off. One high dimension means mid: a plan, a competing alternative, two independent reviews, and a final fresh read. All four happened, and all three verdicts were rejections until the last rewrite.

The plan

P0 Fix the front door

Check that environment variable against the three words it is allowed to be. Sort out the guard that cannot fire. Inspect what actually gets built, after it is built, rather than inspecting the settings that were meant to produce it. Depends on nothing; useful alone.

proves itself by: a test that sneaks forbidden content into the built output and demands the build fail · a build that lies about its mode being refused · the ordinary build still clean

P1 Measure, and change nothing

Time the whole run — including the chain starting up, which happens before the test runner even launches, and which every previous estimate missed. Produce a breakdown that says where the forty minutes go, and answers one question with a number: is the slow claim proof actually the bulk?

proves itself by: a breakdown that adds up to the clock on the wall, and one sentence with a number behind it

P2 Split across machines

Run the suite on three machines instead of one, splitting by naming files rather than letting the runner guess. The subtlety: the test runner stays quiet when a split is misconfigured and runs nothing, so the check is that the tests which actually ran match the list of tests that exist.

proves itself by: the tests that ran equalling the tests that exist · the slowest machine beating a target set from the measurement · the total machine-time staying under a ceiling you approve

P3 The fast lane, on every push

Record what the page asks for once; replay it forever, with no chain running. Three tests move there to begin with — the ones that never sign in. The trap is a recording that goes stale and still passes, so the recording is tied to the contracts and layout it was taken against, and the lane must fail when they change.

proves itself by: running green with no chain anywhere · the stats lane it borrows from still green · a deliberately outdated recording failing rather than passing

P4 Stop building what a run does not need

Two switches: skip the second deployment, skip the native prover. Only worth building if the measurement says so. Anything skipped must make the tests that need it fail loudly — today a missing prover makes them quietly skip, and the run goes green having tested nothing.

proves itself by: each missing piece causing a named failure rather than a skip · the saving measured against the baseline

P5 Turn off the slow proof — only if the numbers justify it

This is the one that trades coverage for speed, so it is last, conditional, and yours to approve separately. If it happens, one test keeps proving for real and must include the honest case: break the mining proof on purpose and require the claim to fail — set up so that nothing else can explain the failure.

proves itself by: the switch provably absent from a real build · the broken-proof test failing for the right reason, shown by passing when the proof is intact

What the reviewers actually said

Review 1 · rejectThe lane could not work, the barriers were fewer than claimed, one variable disabled all of them.
Review 2 · rejectSame conclusions independently, plus: the fast lane already exists in this repo and the plan reimplemented a worse one.
Review 3 · reject"Materially responsive" — but the gates could still pass while proving nothing. Those are now tightened.

Three rejections is normally a sign that the work is bigger than the plan admits. Here it was mostly that a plan about testing was making claims it had not tested. The corrections are all in the plan, and the reviews are on the record beside it.

Three decisions I did not make for you

  • Machine time. Three machines finish sooner but bill more, because each one starts its own chain and does its own build. The measurement will say by how much; the number becomes a ceiling you approve before the split ships.
  • When the fast lane runs. Every push on every branch catches more and is noisier on unfinished work; pull requests only is quieter. Your test filters are written for pull requests today, so "every push" is a real change rather than a line.
  • Whether to do the last step at all. Turning off the slow proof means most claim tests stop exercising it. I would not decide that on a guess, which is why nothing in the plan depends on it and it sits last.

What I need from you

  • Answer the three decisions above, or say "decide after the measurement" for any of them.
